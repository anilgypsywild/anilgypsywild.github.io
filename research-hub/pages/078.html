Research article

outcome-based browsing concept: Lyssna Test Plan

Date: 2026-03-31

Summary

  • This study is a quick comparative Lyssna test to evaluate whether the updated outcome-based browsing concept (the browse concept) homepage direction performs better than the current Causes experience on early-stage cause discovery, comprehension, trust, and giving intent.
  • The goal of this wave is not to prove live business lift. The goal is to determine whether the updated direction is strong enough to move forward into build, and to make the criteria for that decision explicit before launch.

Decision To Inform

This study is meant to answer one decision:

Does the the browse concept homepage direction outperform the current Causes experience strongly enough on early-stage homepage behavior and perception to justify moving into build?

Conditions

Control

Variant

Causes homepage experience

the browse concept homepage prototype

Both conditions should use the same or equivalent causes so the comparison remains fair.

Lyssna Testing Plan

The study will use a comparative unmoderated Lyssna design in which each participant sees both conditions.

To control for order effects, the test should be built in two mirrored versions:

  1. Version A: control first, then variant
  2. Version B: variant first, then control

Split completes evenly across both versions.

Each condition will use the same compact sequence:

  1. Cause Discovery First-click task on the homepage discovery screen
  2. Category / Filter / Sort First-click task on narrowing and browsing controls
  3. At-a-Glance Understanding Brief cause-card view followed by recall and clarity questions
  4. Trust Assessment Rating and open-text response based on the homepage / selected-cause context
  5. Giving Intent Rating and open-text response about likelihood to continue toward donation
  6. End-of-study UX ScoreCard UMUX Q1, UMUX Q2, CSAT, and NPS

The operational Lyssna task script is a separate artifact and follows this brief.

Study Scope

In scope

  1. homepage cause discovery
  2. category / filter / sort clarity
  3. at-a-glance cause-card understanding
  4. homepage-level trust and credibility cues
  5. stated giving intent

Out of scope

  1. cause detail page UX
  2. donation form or payment flow
  3. broader site conversion claims
  4. new exploratory concepts outside the current the browse concept direction

🔎 Core Learning Goals

  1. Determine whether participants can find a relevant cause more easily in the updated experience.
  2. Determine whether the updated category labels and filter path are clearer and more usable.
  3. Determine whether updated cause cards communicate purpose more clearly at a glance.
  4. Determine whether the updated experience increases trust in Compassion and the platform.
  5. Determine whether the updated experience increases stated likelihood to donate.

Primary Measures

Behavioral

  1. first-click target
  2. time to first click
  3. whether participants use category / filter / sort as intended
  4. comprehension accuracy from the quick cause-card task

Rating-based

  1. clarity ratings
  2. trust ratings
  3. giving-intent ratings
  4. end-of-study UMUX, CSAT, and NPS

Qualitative

  1. what made a cause stand out
  2. what made the interface feel clear or unclear
  3. what influenced trust
  4. why participants would or would not continue toward donation

Success Metrics That Still Need Definition

The study should not launch with only general goals like "better" or "clearer."

Design and Product still need to define the decision thresholds for control vs variant before results come back. Otherwise the team will be forced into post-hoc interpretation.

Required pre-launch alignment

Construct Lyssna measure Comparison frame What Design / Product still need to define
Cause discovery first-click rate to a cause or intended exploration path; time to first click variant - control minimum meaningful improvement and maximum tolerable off-target clicks
Category / filter clarity clarity rating; misclicks; open-text confusion themes variant - control what counts as an acceptable narrowing experience
At-a-glance understanding open-text outcome recall; clarity rating variant - control what counts as a correct understanding and what difference is meaningful
Trust mean trust rating; trust-driver themes variant - control minimum meaningful trust lift or minimum acceptable trust threshold
Giving intent mean likelihood-to-donate rating; intent rationale variant - control minimum meaningful uplift that would support moving into build
End-of-study UX scorecard UMUX, CSAT, NPS descriptive and comparative whether these are decision-gating or supporting only

Recommended decision language

Before launch, the team should explicitly agree on one of these:

  1. a minimum acceptable threshold for each primary measure
  2. a smallest effect size of interest for each control-vs-variant comparison
  3. both, if the team wants a cleaner build / revise / pause rule

Sample Recommendation

  • Recommended: 18 completes total
  • Minimum viable: 12 completes total

This is enough for directional comparison and common-issue detection in a paired design. It is not intended to estimate live KPI lift or detect small effects.

Statistical Framing

This is a within-subject comparative design, so each participant sees both conditions and serves as their own control.

That supports directional comparison, but it does not turn a small prototype study into production-grade KPI validation.

The practical implication is:

  1. 12 completes is acceptable for minimum-viable directional evidence
  2. 18 completes is the stronger default for comparative read quality
  3. neither sample should be described as proof of live CTR or conversion improvement

📓 Deliverables

The deliverable from this wave will be a concise comparative readout showing:

  1. where the variant outperformed control
  2. where the variant still created confusion or weak trust signals
  3. whether the variant is ready to move forward, needs revision, or should pause before build

Next Steps

  • The next artifact is the operational Lyssna task script and build setup, using the prepared screenshot stimuli for both conditions.
